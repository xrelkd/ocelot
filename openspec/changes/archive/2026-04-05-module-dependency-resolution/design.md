## Context

`ocelot-bootstrap` runs as PID 1 in QEMU VM initramfs. It loads kernel modules via `finit_module(2)` before mounting the root filesystem. Current `ModulesConfig` has two modes:

- **List**: loads user-specified module names in order — no dependency awareness
- **Scan**: loads all `.ko`/`.ko.xz`/`.ko.gz` files from a directory in filesystem order — no dependency awareness

Both modes log warnings on failure and continue, meaning a module that fails due to unmet dependencies is silently skipped.

The Linux kernel's `modules.dep` file (generated by `depmod`) encodes the full dependency graph as `module_path: dep1 dep2 ...`. This is the authoritative source of truth for module ordering.

### Architectural Constraint: Bootstrap Purity

`crates/bootstrap` is a pure library crate with **no serde dependency**. All config types are plain `#[derive(Clone, Debug)]` structs. Serde deserialization lives exclusively in `ocelot/src/config/bootstrap.rs` (the binary crate). The two layers communicate via `From::from` conversions — ocelot's serde-enabled types convert into bootstrap's plain types. This separation must be maintained: **no serde derives in `crates/bootstrap`**, **no mixing of config types between the two layers**.

### Architectural Decision: Dependency Resolution in Ocelot

Cyclic dependency detection and topological sorting are performed in the **ocelot binary** during config validation, not in the bootstrap library. This reuses the existing `petgraph` dependency and the SCC/cycle detection patterns already in `ocelot/src/config/supervise.rs`. Bootstrap receives module names that are already in correct dependency order.

## Goals / Non-Goals

**Goals:**

- Allow users to provide a `modules.dep` path so ocelot can auto-resolve loading order before passing config to bootstrap
- Detect cyclic dependencies during config validation and abort with a clear error listing all involved modules
- Ignore extra entries in `modules.dep` that are not needed by the user's module list
- Keep bootstrap lightweight — no new external crate dependencies, no structural changes to bootstrap types
- Reuse ocelot's existing petgraph dependency and cycle detection patterns
- Maintain strict separation between bootstrap library types and ocelot serde types

**Non-Goals:**

- No support for `modules.softdep`, `modules.alias`, or other modprobe metadata
- No runtime dependency resolution (kernel handles missing built-in deps at load time)
- No modification of `modules.dep` — it is read-only input
- No support for module parameters via depfile
- No serde in `crates/bootstrap`
- No structural changes to `crates/bootstrap` types (documentation only)

## Decisions

### 1. Schema: Add fields to ocelot's serde types only

`ModulesConfig::List` in `ocelot/src/config/bootstrap.rs` gains `dep_file_path: Option<String>`. `ModulesConfig::Scan` gains `dep_file_path: String` (required) and `names: Option<Vec<String>>` (optional filter).

Bootstrap's `ModulesConfig` in `crates/bootstrap/src/config.rs` is **unchanged** — no new fields needed.

**Rationale**: Ocelot owns config parsing and validation. After sorting, it passes only the ordered `names` list to bootstrap. Bootstrap doesn't need to know about depfiles.

### 2. Config separation: parallel types with `From::from` conversion

The `crates/bootstrap/src/config.rs` types remain plain (no serde). The `ocelot/src/config/bootstrap.rs` types gain matching fields with `#[derive(Deserialize)]`. Conversion is done via `impl From<ocelot::ModulesConfig> for ocelot_bootstrap::ModulesConfig` at the boundary. The `From` impl strips `dep_file_path` and passes the sorted `names`.

**Rationale**: This preserves the existing architectural pattern. Bootstrap stays a pure library; ocelot owns all serialization and validation concerns.

### 3. Module identity by basename, not full path

The dependency map keys are module basenames (e.g., `virtio_net.ko.xz`), not full paths. When resolving deps for `virtio_net`, we match by basename against the depfile entries.

**Rationale**: `modules.dep` uses relative paths under the kernel version directory, but users specify module names without paths. Basename matching bridges this gap.

### 4. Reuse petgraph for topological sort and cycle detection

Ocelot already depends on `petgraph`. The existing pattern in `ocelot/src/config/supervise.rs` (`detect_dependency_cycles()` using Kahn's toposort + Kosaraju SCC + DFS cycle extraction) is reused for module dependency validation.

**Rationale**: No new dependencies. Consistent error messages across the codebase. Proven implementation.

### 5. Validation at config load time, not boot time

Cyclic dependency detection and topological sort happen in `BootstrapConfig::validate()`, before `to_bootstrap_config()` is called. If validation fails, boot never starts.

**Rationale**: Fail fast. Users get clear error messages at config time rather than cryptic module load failures during boot.

### 6. Bootstrap receives pre-sorted names; no Result change

After validation, `From::from` passes the sorted `names` list to bootstrap. `load_modules()` continues to return `()` with best-effort semantics (warnings on failure). No `Result` change needed.

**Rationale**: Bootstrap's job is simple — load modules in the given order. If a module fails to load (e.g., already built-in), log a warning and continue. The ordering guarantee comes from ocelot's validation.

### 7. Bootstrap doc comments clarify the assumption

`ModulesConfig` in `crates/bootstrap/src/config.rs` gets doc comments stating that `names` are assumed to be in correct dependency order, as validated by the ocelot config layer.

**Rationale**: Future maintainers understand the contract between ocelot and bootstrap without needing to trace through the `From` impl.

### 8. Test data via `include_bytes!`

Test fixtures are stored as `.dep` files under `ocelot/src/config/test_data/` with descriptive basenames and loaded via `include_bytes!` in unit tests. The happy-path fixture is derived from a real Linux kernel's `modules.dep` (virtio subsystem subset).

Fixtures:

- `modules-virtio.dep` — real kernel virtio subsystem deps (happy path)
- `modules-cycle.dep` — 2-node cycle (virtio_net ↔ virtio)
- `modules-cycle3.dep` — 3-node cycle (a → b → c → a)
- `modules-selfloop.dep` — self-loop (a → a)
- `modules-empty.dep` — empty file

**Rationale**: Tests are self-contained, reproducible, and don't depend on the host system having a specific kernel version installed.

## Risks / Trade-offs

| Risk                                              | Mitigation                                                                                    |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `modules.dep` format changes in future kernels    | Parse only the `path: deps` line format; fail gracefully with clear error                     |
| Large depfiles (7000+ entries) cause slow parsing | Kahn's Algorithm is O(V+E); for 7K modules this is sub-millisecond                            |
| Module names with special characters in paths     | Use basename-only matching; full path used only for `finit_module` call                       |
| Scan mode with depfile loads unexpected modules   | `names` field lets users filter; without it, all `.ko` files in the scan directory are loaded |
| Bootstrap used directly without ocelot            | Bootstrap still works — it just loads modules in user-specified order without validation      |
| Config drift between ocelot and bootstrap types   | `From::from` conversion at the boundary catches field mismatches at compile time              |
